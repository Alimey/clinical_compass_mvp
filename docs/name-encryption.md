# Имена пациентов и выгрузки

Имена в `users.name` хранятся в зашифрованном виде. Это относится к пациентам, специалистам и близким. Сервер расшифровывает имя после загрузки записи для обычной работы кабинетов; права доступа к карточкам и переписке сохраняются.

Используется Fernet из `cryptography` — AES-128-CBC с проверкой подлинности HMAC-SHA256. Из отдельного 32-байтного ключа хранения через HKDF получаются разные ключи для имён и служебных данных. При повторном шифровании одного имени получаются разные строки.

## Область защиты

| Данные | Хранение |
| --- | --- |
| Имена аккаунтов | Шифротекст в `users.name` |
| Тексты внутренних уведомлений | Шифруются: они могут содержать имя пациента |
| Промежуточная анкета и исходящая очередь Telegram | Шифруются до отправки через настроенное подключение |
| Сохранённые ответы повторяемых запросов | Шифруются в таблице `idempotency` |
| Остальные поля базы | Прежний формат хранения |

Это шифрование выбранных полей, а не всего файла SQLite. Телефоны, дневники, переписка и другие произвольные тексты не переводятся этим изменением в зашифрованное хранилище. Если имя вручную написано в таком тексте, оно также может оставаться открытым. Доступ к работающему серверу с ключом позволяет расшифровать защищённые поля.

HTTPS защищает передачу. Зашифрованная офлайн-копия пациента использует прежний PIN и отдельный механизм AES-GCM в браузере.

## Ключ хранения

Локально приложение автоматически создаёт `patient-names.key` рядом с рабочим файлом БД. Например, для `instance/compass.db` это `instance/patient-names.key`. В Linux файл создаётся с правами `0600`; на Windows действуют права доступа к папке и файлу.

Для сервера доступны два способа:

- `COMPASS_NAME_KEY` — постоянный ключ в переменной окружения.
- `COMPASS_NAME_KEY_FILE` — путь к существующему файлу ключа; без настройки используется файл рядом с БД.

Переменная `COMPASS_NAME_KEY` имеет приоритет. Ключ не хранится в SQLite, не отправляется браузеру и не добавляется в Git или Docker-контекст. Каталог БД и файл ключа должны сохраняться между перезапусками; в Docker они находятся на томе `/data`.

Перед первым включением шифрования на сервере можно создать ключ в своём терминале:

```bash
python -m compass.name_crypto --generate-key
```

Сохраните результат в защищённом хранилище секретов и задайте как `COMPASS_NAME_KEY` на Render. Команда выводит секрет: не добавляйте его в репозиторий, отчёт или переписку.

**Если приложение уже создало зашифрованную БД**, для перехода с файла на переменную окружения используйте именно текущий ключ из `patient-names.key`. Новый случайный ключ не подходит. Ротация ключа этой версией не выполняется автоматически. При потере или неверном ключе запуск с зашифрованной базой прекращается; данные не перезаписываются новым ключом.

## Существующая база

Перед обновлением остановите предыдущий локальный процесс приложения. На первом запуске открытые имена и перечисленные служебные поля автоматически преобразуются. Уже зашифрованные значения повторно не шифруются.

Перед преобразованием создаётся зашифрованный снимок `<имя-базы>.before-names-<дата>.enc`. Миграция записывается транзакцией. Затем SQLite очищает старые страницы и WAL-журнал. Если очистка заблокирована другим процессом, запуск прекращается с просьбой остановить его; очистка повторяется при следующем запуске.

Для восстановления предмиграционного снимка в новый файл:

```bash
python -m compass.name_crypto --restore-backup instance/compass.db.before-names-ДАТА.enc --output instance/recovered.db --key-file instance/patient-names.key
```

Либо используйте `COMPASS_NAME_KEY`. Существующий файл назначения не перезаписывается. Восстановительный файл содержит состояние до завершения миграции, в том числе прежние открытые поля; храните его в защищённом месте и запускайте приложение с этим файлом и тем же ключом для преобразования.

Обычная резервная копия через `compass.backup` сохраняет зашифрованные значения имён. Для её запуска в другом каталоге или на другом сервере потребуется тот же ключ. Сохраняйте ключ отдельно от копии БД.

Ранее созданные резервные копии и уже скачанные файлы автоматически не преобразуются.

## Скачиваемые файлы

- Исследовательский CSV сохраняет прежние агрегаты и код пациента `PK-…`. Имена, телефоны, дневник и чат не добавляются.
- В TXT с результатом анализа врач и пациент получают тот же код вместо имени. Из заголовка, результата и примечания заменяются точное известное имя и отдельные части имени без учёта регистра.
- Полная БД не выгружается через эти кнопки.

Замена в произвольном тексте не является полной анонимизацией: склонения, опечатки, другие люди и иные идентифицирующие сведения требуют отдельной проверки. Сами CSV и TXT не шифруются — выбран код пациента без имени, а не зашифрованный файл.

## Проверки

`tests/test_name_crypto.py` проверяет шифротекст в SQLite, читаемые имена в разрешённых кабинетах, новые аккаунты, повторный запуск, миграцию и восстановительный снимок, неверный/потерянный ключ, повреждение шифротекста, Telegram, внутренние уведомления и выгрузки для обеих ролей.
